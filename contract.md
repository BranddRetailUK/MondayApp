# Ultimate Hub Service Contract

Last reviewed: 2026-10-02

## Purpose

Ultimate Hub is a Node/Express service backed by Railway Postgres. Its production surfaces are the Tuesday Dashboard, the full DATABASE order/customer workflow, Hub authentication, and Cloudinary-backed dashboard files.

Production data boundaries:

1. Tuesday Dashboard jobs, status, priority, approvals, dates, designs, line items come from Railway Postgres.
2. Dashboard file metadata is stored in Railway Postgres; file bytes are delivered by Cloudinary.
3. Label printing reads the DB-backed Tuesday board payload, prepares status through the DB-backed label endpoint, and renders job, customer, and title text without a QR or other scannable code.
4. DATABASE orders and historical snapshots are populated from MDB snapshots and manual DATABASE entries. The normalized Ralawise catalogue is the source of truth for active stock-product search and colour/size selection; legacy Access product/order IDs remain immutable historical references.
5. The running service has no external work-management OAuth, API client, webhook, board-sync, asset-proxy, or status-write connection.

## Entry Points

- Runtime entry: `server.js`, which loads `server.modular.js`.
- App composition: `src/app.js`.
- Static frontend: `public/`.
- Browser entry pages advertise theme-aware PNG favicons: the black Ultimate icon is selected for light browser themes and the white Ultimate icon is selected for dark browser themes.
- Hub auth: `/login` and `/signup` serve the app login/signup page. `/` and `/index.html` require a Hub session. Full-access users may use DATABASE, Tuesday Dashboard, and `/database-job.html`; `dtf_only` users are restricted to DTF Uploader and its owned upload APIs.
- Ultimate Hub exposes Dashboard, DATABASE, Holiday Board, File Viewer, and a production-account-only DTF Uploader navigation item. Dashboard is the navigation label for the existing Tuesday Dashboard (`test-dashboard`) and remains the default for full users; DTF Uploader is forced for `dtf_only` users. The active tab is stored in browser localStorage unless a matching `?tab=` value or hash explicitly selects one. DATABASE also stores its current in-app view in browser localStorage, including Lami DTF, the active order/customer tab, and selected order/customer where applicable.
- DB bootstrap: `src/db/migrate.js`.
- Config: `src/config/env.js`.

## API Endpoints

### Ultimate Hub Auth

- `GET /login`: serves the Hub login/signup page in login mode.
- `GET /signup`: serves the same page in signup mode.
- `GET /api/auth/me`: returns `{ user }` for the current Hub session, or `null`; authenticated users include `access_scope` as `full` or `dtf_only`.
- `POST /api/auth/signup`: accepts a signup request for any syntactically valid email address. It validates the submitted name and password, stores a scrypt password hash in `hub_signup_requests`, returns HTTP 202 with `Your request has been received.`, and does not create a user or session. A repeated pending or rejected request for the same email refreshes that request; a request matching an existing user receives the same generic response without changing that user.
- `POST /api/auth/login`: verifies email/password against `hub_users` and starts a session. Pending and rejected signup requests are not users and cannot log in; all `hub_users` rows that existed before the request workflow remain active without requiring review.
- `POST /api/auth/logout`: deletes the current session and clears the cookie.

Security rules:

- Passwords are stored only as Node `crypto.scrypt` hashes with per-user random salts.
- New signup passwords must be 12-128 characters, cannot be highly predictable, and cannot contain the submitted name or email identity. Signup never stores or returns plaintext passwords.
- Signup and login requests have per-IP/account rate limits. Login uses the same generic invalid-credentials response and performs a dummy scrypt verification for unknown users to reduce account-enumeration timing differences.
- Signup responses do not reveal whether an email already has an account or request. Only authenticated users with `hub_users.can_manage_users = true` can read, accept, or reject pending requests through the protected DATABASE API. The migration grants this permission to existing users; accounts created through the request workflow default to false and cannot administer other users.
- Accepting a pending request transactionally inserts it into `hub_users`; the DATABASE reviewer chooses ordinary `full` access with Accept or uploader-only `dtf_only` access with Lami DTF. Rejecting it leaves no login-capable user. Both decisions immediately erase the request's stored password hash and record reviewer audit metadata.
- Session cookies are `HttpOnly`, `SameSite=Lax`, and `Secure` in production/HTTPS.
- Database session rows store only a SHA-256 hash of the random browser session token.

### Health And Status

- `GET /health`: returns `{ ok: true }`.
- `GET /api/status`: returns `{ ok: true, hubAuthenticated: boolean }`.

### DTF Uploader

- `POST /api/dtf/jobs`: creates a DTF job plus 1-40 expected PDF file rows for the logged-in user. Each file is limited to 250MB and quantity 1-99. The server calculates £14.00 net per sheet plus 20% VAT in integer pence and allocates a concurrency-safe `DTF-000001` style number.
- `POST /api/dtf/uploads/sign`: verifies ownership of an expected file, marks it uploading, and returns a short-lived signed Cloudinary `image/authenticated` upload payload for the exact `ultimate-hub/dtf/{userId}/{jobId}/{fileId}` public id.
- `POST /api/dtf/uploads/finalize`: ignores browser URLs and verifies the exact asset through Cloudinary. A valid file must be an authenticated PDF image resource, 1-250MB, with exactly one page whose positive width is no more than 550mm and whose length is 900-1100mm; the three-point PDF metadata tolerance remains at the maximum-width and minimum/maximum-length boundaries. Invalid or failed assets are destroyed and the file/job becomes failed; all verified files move the job to received.
- `POST /api/dtf/layouts/eps-preview`: accepts an authenticated user's EPS file up to 25MB, converts it temporarily through Cloudinary to lossless 300-DPI PNG, returns that PNG, and destroys the temporary asset.
- `GET /api/dtf/files/:fileId`: authorizes the submitting owner or any full user and redirects to a five-minute signed Cloudinary PDF. `?download=1` requests attachment disposition for the Lami DTF Download PDF action; without it the admin Open PDF action previews the same verified premade or generated gang sheet.
- `GET /api/dtf/admin/jobs` and `GET /api/dtf/admin/jobs/:jobId`: full-user-only paginated DTF job summaries and file details for the DATABASE Lami DTF page.
- `PATCH /api/dtf/admin/jobs/:jobId`: full-user-only transition to RECEIVED, IN_PRODUCTION, COMPLETED, or FAILED with updater/timestamp audit fields.
- Job creation is limited to 20, sign/finalize calls to 240 each, and EPS conversions to 30 per user per 15 minutes through Postgres-backed rate-limit buckets.

DTF UI rules:

- DTF Uploader contains only the UltimateHub shell plus Upload Gang/Create Gang modes; the standalone BRAND header, home, profile, login, and customer history are not ported. Upload mode shows the page title without supporting copy, and its upload card ends after the PDF list so pricing and submission actions sit directly beneath it; layout creation remains available from the Create Gang mode tab.
- Premade sheets are browser-validated with PDF.js before job creation using the same one-page, maximum-550mm-width, and 900-1100mm-length rule as server finalization. Multiple PDFs and quantities may be combined in one job, previewed individually, and persisted as unsent per-user IndexedDB drafts. The upload preview has no separate Preview/filename heading and grows to the full rendered sheet height without an internal scrollbar. Valid file rows omit the green size-confirmation line and file-size text while checking and error text remain visible; the quantity controls and delete X sit beneath the full-width wrapping filename. The empty upload icon/instructions are centered as an overlay inside the preview window and are hidden when its PDF canvas is shown. The upload card begins with `Add gang sheet PDFs` without an extra arrow icon. The headline price shows the net subtotal followed by smaller purple `+ VAT`; the existing Sheets, Subtotal, VAT, and Total breakdown remains below in black. Files over 100MB use Cloudinary's signed REST chunk protocol with contiguous 20MB ranges, a per-file upload id, and progress after every chunk so the advertised 250MB ceiling does not depend on the ordinary request-size limit.
- The layout editor accepts PNG, EPS, and one-page PDF artwork on a fixed 550 × 1000mm sheet. New artwork retains its source physical dimensions: PNG uses its pHYs resolution or a 300-DPI print fallback, EPS uses its HiResBoundingBox/BoundingBox or the 300-DPI preview fallback, and PDF uses the one-page media size. Oversized source artwork is rejected instead of normalized. Background and Artwork gap controls share the first row with a thin purple divider; the gap uses the same purple heading style, and each light/grey/dark selector visually mirrors its canvas background. The artwork-gap stepper is compact and keeps `mm` directly beside its number. The artwork action reads `Upload PNG, EPS or PDF`, and the canvas panel has no separate Preview heading or dimensions pill. The editor supports a 0-250mm gap (10mm default), light/grey/dark backgrounds, keyboard-editable proportional W/H controls, copies, group/individual 90-degree rotation, selection/z-order, deletion, dragging, and automatic non-overlapping packing capped at 80 pieces. Automatic packing fills each available row from left to right before wrapping down to the next row. The canvas artwork prompt is shown only while the layout is empty, including while an initial EPS is being processed, and hides as soon as the first artwork is accepted. EPS conversion displays a blocking loading wheel over the canvas until processing succeeds or fails.
- Generated PDFs use `pdf-lib`: PNG bytes and one-page PDF artwork are embedded independently without whole-sheet rasterization; EPS uses the returned 300-DPI PNG. The output is one exact 550 × 1000mm PDF page and is added back to the upload draft.
- DATABASE home exposes a blue Lami DTF button. Its admin view shows job number/date/customer/email, files, sheet quantity, subtotal, VAT, total, status, per-file upload detail, signed PDF links, and the status control.

### Holiday Board

- The `holiday-board` tab uses the existing dark Hub shell with light-blue grid borders, weekday headings and month labels, a simple Holiday Board heading without a calendar footer/legend, and a Monday-first, 37-column year planner: January–December each occupy one horizontal row, offset by the first weekday. Weekends are shaded, today has a solid light-blue background and dark date number, and spacious 74 × 94px minimum day boxes scroll horizontally and vertically with sticky month/weekday labels. Calendar-only pinch zoom (trackpad and two-finger touch) scales from a dynamically calculated whole-year fit to the original 100% maximum, preserves zoom across edits, and leaves normal scrolling unchanged. Initial desktop views (fine pointer and at least 961px wide) default to Fit year; mobile defaults to the original readable 100% size. Vector date-number labels scale down with the cells without mobile minimum-font inflation. Compact − / Fit year / + controls sit alongside the user dots, without a percentage box, and provide an alternative.
- Top-row person dots can be dragged onto editable dates to place a full-day marker; selecting a person and clicking a date provides a keyboard/touch alternative. Multiple 54px grid dots share one row with 80% horizontal overlap and fully opaque fills, keeping day boxes at a consistent height. Hovering a date with multiple people shows an unscaled mouse-following popup with each person’s circle, name and full/morning/afternoon label, without a date heading; it stays inside the viewport and hides on leaving the date, scrolling, zooming, opening a dialog or losing window focus. Clicking an individual 54px grid dot cycles full day → morning → afternoon → removed without affecting other people on the date. A right-click (or Shift+F10) on a top-row person opens preset/custom colours and updates all their dots, including historical ones. Colours are stored in Postgres per registered user (not browser storage); each device loads those saved colours on opening or refreshing the board. Calendar scroll position is retained after edits. Successful date/colour changes do not leave update messages; save failures remain visible.
- Past dates are read-only: no additions, portion changes or removals before today in Europe/London. The server rejects any date range starting in the past without partial changes. Today and future dates remain editable; person colour settings apply across the full board.
- Full-access Hub users can view and edit the shared board. Uploader-only accounts cannot access its APIs or tab. Manage people selects registered `hub_users` (pending signup requests are excluded), assigns 1–3 alphanumeric circle letters and a hex colour, and updates that person's circles across all years. New login accounts still use the existing signup/review workflow.
- `GET /api/holiday-board?year=YYYY` returns registered user IDs/names, board members, and that year's holiday dates; years are limited to 2000–2100. No email or authentication fields are returned.
- `PUT /api/holiday-board/members/:id` adds or updates an existing registered user's `{ initials, colour }`.
- `POST /api/holiday-board/days` accepts `{ userId, start, end, weekdaysOnly, action }`, where action is `add` or `remove`. An optional `portion` is `full` (default), `am` (left half-circle), or `pm` (right half-circle). Adding an existing date replaces its portion. Inclusive ranges are limited to 366 days; invalid dates and unknown members are rejected. Additions are idempotent, multiple users can share a day, and removals affect only the selected person/dates.

Missing/ambiguous users defer the entire import. The two unresolved photo marks remain excluded. Local preview test edits are not promoted.
- `holiday_board_members` stores circles linked to registered users. `holiday_board_days` stores unique user/date pairs, full/morning/afternoon portion, and creator/timestamp; deleting a registered account cascades its membership and dates. Both tables are created idempotently by bootstrap.

It reads registered names once, then persists holiday edits only to `/tmp/ultimate-holiday-preview.json` (or `HOLIDAY_PREVIEW_FILE`). ### Tuesday Dashboard

- `GET /api/test-dashboard/board`: returns the Tuesday Dashboard payload from Railway/Postgres `database_jobs`, `database_job_line_items`, `database_job_positions`, and test-dashboard state/file tables. File values contain Cloudinary `secure_url` metadata only. While the Dashboard tab is visible, the browser refreshes the full board every three seconds; hidden or inactive tabs skip the refresh.
- `PUT /api/test-dashboard/items/:jobId/status-column`: updates DB-backed or private dashboard `STATUS` / `PRIORITY` state. Body is `{ "columnId": "...", "label": "..." }`, or `{ "columnId": "...", "clear": true }` for clearing `PRIORITY`. DB-backed rows write `test_dashboard_job_state` and `database_jobs.dashboard_status` / `dashboard_priority`; private rows write only `test_dashboard_private_jobs`. The route applies local status-driven group moves, completed cleanup, invoiced archive, and priority clearing. `PRE-PRODUCTION` is not selectable in STATUS; the group remains reachable through job approval / `NO STOCK`. `AWAITING APPROVAL` uses the ordinary `#2b2b2c` dashboard background with white text. Only the exact Hub account email `melvyn@ultimatepromotions.co.uk` is blocked from setting any Tuesday Dashboard `STATUS` to `COMPLETED`: the browser blocks the request and shows `LEAVE IT ALONE MELVYN` in a dedicated dialog sized to 50% of the viewport width and height, with an Okay dismissal button; the API independently returns `403` with `dashboard_completed_status_blocked`. Other users, including `Ultimate Production`, other status changes, and other dashboard dialog sizes are unaffected. A Print + Emb job cannot be changed to `READY TO PRINT` until both `TRANS` and `JAQ` are checked; the API returns `split_job_ticks_required` plus the missing tick names without changing status. `STATUS = COMPLETED` normally moves to COMPLETED; for an active Print + Emb split, the virtual Print and Embroidery row ids store independent dashboard-only branch statuses and the aggregate `database_jobs.dashboard_status` remains `READY TO PRINT` until both branches are complete. The first completed branch stays in its production group; the second completion atomically removes the split state, restores the one canonical dashboard row, and moves it to COMPLETED. `STOCK ORDERED` preserves the current non-production group until approval; `TO SAMPLE` moves to TO SAMPLE; and `SAMPLED` moves to OFFICE. `database_jobs.is_complete` remains the imported closed/invoiced flag and is not set merely by dashboard `COMPLETED`.
- Sampling approval gate: a DB-backed or private job that has been `TO SAMPLE` cannot have `JOB ✔` checked until it has previously reached `SAMPLED`. Current sample status/group and the existing `database_job_status_updates` status/previous-status history determine the rule for DB-backed jobs, including jobs subsequently moved to OFFICE or HOLD. Private rows retain the same lifetime sampling flags in `column_values.__dashboard_sampling`; changing group/status does not reset them. A prior `SAMPLED` continues to satisfy the rule if the job returns to TO SAMPLE. The board exposes `dashboard_sampling` (`required`, `sampled`, `blocked`) for immediate browser validation; the checkbox API independently returns HTTP 400 / `sample_required` before changing job approval, status, group, dates, or priority. The existing design and visual requirements still apply after sampling. Selecting `READY TO PRINT` is also rejected while sampling is outstanding; canonical DB-backed jobs additionally require `JOB ✔` approval (HTTP 400 / `job_approval_required`). Both failures show an explanatory Okay dialog and retain the current row/group. Successful status-column responses and DATABASE updates use the effective post-automation label, preventing the former requested-status/dashboard-state mismatch.
- `POST /api/test-dashboard/private-jobs`: creates a dashboard-only private job row in `test_dashboard_private_jobs`, usually in OFFICE. These rows are not `database_jobs`, do not allocate job/order/invoice numbers, and do not appear in DATABASE.
- `DELETE /api/test-dashboard/private-jobs/:jobId`: permanently deletes a dashboard-only private job row and rejects normal DB-backed ids. Any Cloudinary proof/design assets referenced by the private row are queued for deletion best-effort.
- `PUT /api/test-dashboard/items/:jobId/name`: renames dashboard-only private jobs. It rejects DB-backed job ids because real order titles stay owned by DATABASE.
- `PUT /api/test-dashboard/items/:jobId/group`: moves a DB-backed or private Tuesday Dashboard row to HOLD, OFFICE, or PRE-PRODUCTION from the row action menu. Moving to PRE-PRODUCTION requires `JOB ✔` approval; unapproved rows are rejected and continue to resolve to OFFICE unless explicitly moved to HOLD. It writes the matching dashboard status label (`HOLD`, `AWAITING APPROVAL`, or `NO STOCK`), except that a row already at `CHECKED IN` retains that status when moved to PRE-PRODUCTION, and updates `database_jobs.dashboard_status` only for DB-backed jobs.
- `PUT /api/test-dashboard/items/:jobId/date-column`: updates the dashboard `DATE` column for DB-backed or private Tuesday Dashboard rows and recalculates `PRIORITY` from the due date (`Critical`, `High`, `Medium`, `Low`). DB-backed jobs with `database_jobs.customer_date_required` keep the DATABASE customer date and reject dashboard date edits.
- `PUT /api/test-dashboard/items/:jobId/checkbox-column`: updates Tuesday Dashboard parent checkbox columns for DB-backed rows in `test_dashboard_job_state.column_values` or private rows in `test_dashboard_private_jobs.column_values`. Body is `{ "columnId": "...", "checked": true|false }`. The route accepts only configured checkbox columns. The `JOB ✔` checkbox is the job-approved flag and is the main driver for whether a job is approved/readiness-approved; DB-backed approval is stored on `database_jobs.proof_approved` / `proof_approved_at`, while private approval stays dashboard-only. Checking `JOB ✔` requires at least one design/PSG reference and at least one file in the Tuesday Dashboard `PROOF` column; otherwise the route returns `approval_requirements_missing`. Successful DB-backed approval records an `APPROVED` activity event, moves the job to PRE-PRODUCTION, preserves `STATUS = STOCK ORDERED` or `CHECKED IN` when either status is already set and otherwise sets `STATUS = NO STOCK`, clears `PRIORITY`, and sets `DATE` to 14 calendar days from approval. Clearing `JOB ✔` returns the job to OFFICE / `AWAITING APPROVAL`, clears priority, and clears date unless a DB-backed customer date is required.
- `PUT /api/test-dashboard/items/:jobId/text-column`: updates the DB-backed Tuesday Dashboard `NOTES` parent text column in `test_dashboard_job_state.column_values`, or private-job text values in `test_dashboard_private_jobs.column_values`. Body: `{ "columnId": "...", "value": "..." }`. DB-backed jobs accept only the mirrored `NOTES` text/long-text column so DES/PSG remains on its design reconciliation route. Private jobs additionally accept the virtual `private_total` field for TOTAL: a non-negative safe whole-number quantity or an empty string to clear it. The board returns this stored value without creating a DATABASE order or subitem; real-job TOTAL overrides are rejected.
- `PUT /api/test-dashboard/items/:jobId/design-column`: reconciles DES/PSG values edited from the Tuesday Dashboard with the related DATABASE Design tab rows. Body: `{ "columnId": "...", "value": "..." }`. Submitted values are split on `/`; each represented design/PSG reference is matched against existing `database_job_positions.design_ref` values. Exact matches are kept, changed refs update an existing row of the same kind where possible, new refs insert rows, and removed refs delete dashboard-created empty rows or clear `design_ref` on rows that still have position/colour data. Exact represented design/PSG references are not inserted twice.
- `POST /api/test-dashboard/items/:jobId/label-printed`: prepares a Tuesday Dashboard label-print event without generating or returning a scanner URL. The event normally sets `STATUS = CHECKED IN` in test-dashboard state and `database_jobs.dashboard_status` while preserving the current group and job-approval state; `CHECKED IN` is an explicit unapproved-status override and is not replaced by `AWAITING APPROVAL`. Reprinting never regresses `COMPLETED`; it also preserves `READY TO PRINT` when the job's resolved group is no longer PRE-PRODUCTION. The label is still prepared and printed when either status is preserved. Private Tuesday Dashboard rows receive the same dashboard-only status automation.
- `POST /api/test-dashboard/uploads/signature`: returns a short-lived signed Cloudinary browser-upload payload. It requires `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and `CLOUDINARY_API_SECRET`; the API secret never reaches the browser. The signed params are limited to Cloudinary upload params that Cloudinary includes in its signature check; PDF delivery handling is done after upload from the original filename and saved metadata. Requests for the underlying `PROOF`/visible `VISUAL` column are rejected unless the filename ends in `.pdf`, `.jpg`, `.jpeg`, or `.png`. The Tuesday Dashboard file cells and DATABASE order `VISUAL` tab share this endpoint; a real `database_jobs` row is sufficient, so Business Gifts can receive stored visuals without acquiring Tuesday Dashboard identity.
- `POST /api/test-dashboard/items/:jobId/files`: saves Cloudinary upload metadata for a DB job/file column in `test_dashboard_files`. For the underlying `PROOF`/visible `VISUAL` column, it also requires the original filename and Cloudinary format to resolve to PDF, JPEG, or PNG, preventing unsupported metadata from bypassing the signature-stage check. DATABASE order-tab uploads write through this same metadata path, including for Business Gifts; non-gift jobs already represented on Tuesday Dashboard therefore show the new file in the dashboard `VISUAL` cell, while gift orders remain absent from the board and retain the file for DATABASE storage/viewing.
- `DELETE /api/test-dashboard/items/:jobId/proof-files`: removes all files from the Tuesday Dashboard `PROOF` column for a DB-backed or private row. DB-backed rows delete matching `test_dashboard_files` metadata; private rows clear the proof payload from `test_dashboard_private_jobs`; Cloudinary assets are destroyed best-effort.
- `DELETE /api/test-dashboard/items/:jobId/files/:fileId`: deletes one test-dashboard file from a DB-backed or dashboard-only private job and best-effort destroys the Cloudinary asset.

### DATABASE

The dashboard has a `DATABASE` tab backed by a full-history MDB import.

Frontend files:

- `public/index.html`: sidebar tab and legacy-style DATABASE hub markup.
- `public/database.js`: DATABASE home screen, manual new-order form, outstanding order grouping, order navigation, order detail tabs, line-item rendering, and design-position rendering.
- `public/database-job.html`: older direct full-width job info page retained as a fallback.
- `public/database-job.js`: older job facts, contact fields, line items, and positions rendering for the fallback page.
- `public/styles.css`: scoped legacy DATABASE hub styles plus older fallback page table styles.

Backend files:

- `src/routes/database.js`: `/api/database` JSON endpoints.
- `src/db/databaseSchema.js`: idempotent table creation.
- `scripts/import-database-mdb.js`: imports `PS_XP_tab.mdb` into Railway/Postgres, including a products-only mode for the full Access product catalogue.

Endpoints:

- `GET /api/database/summary`: returns counts for jobs, line items, positions, products, customer addresses, customer contacts, import status, counts by year, and counts by type.
- `GET /api/database/reports?range=daily|weekly|monthly|mtd|ytd|last12|custom-month|custom-year`: returns the DATABASE Analytics & Reports financial payload using job order date with source-created date fallback and Europe/London period boundaries. Daily means today with hourly graph buckets; weekly is the trailing 7 days with daily buckets; monthly is the trailing 30 days with daily buckets; month-to-date uses daily buckets; year-to-date uses monthly buckets and accepts an optional validated `year=YYYY`; and last12 is the rolling 12 calendar months with monthly buckets. `custom-month` requires `period=YYYY-MM` and returns that complete calendar month in daily buckets, while `custom-year` requires `period=YYYY` and returns that complete calendar year in monthly buckets. Missing graph buckets are returned as zero. Financial values use non-internal invoiceable line items: net sales are `quantity * unit_price`, VAT follows the invoice child/youth zero-rating rules and otherwise normalizes stored decimal/percentage VAT rates, gross sales are net plus VAT, COGS are `quantity * unit_cost`, and gross profit/margin are net sales less COGS so VAT does not inflate profit. The response includes totals, average order value, units, missing price/cost coverage counts, capped top-five customers, sales by order type, the highest-grossing order, the available order years used by the report selectors, and every order in the selected period with order/customer/job identity plus gross sales, net sales, COGS, and gross profit.
- `GET /api/database/jobs?q=&customer=&type=&year=&status=&limit=&offset=&includeTotal=`: returns paginated jobs. Default and UI page size is 100 jobs. `includeTotal=false` skips the count query and returns `hasMore` from a one-row lookahead; the All Orders UI uses that path for active searches and follow-up page loads so it does not execute the broad search twice before showing the first page. Supported `status` filters include `open`, `complete` / `completed`, and `to-invoice`; `open` excludes legacy-closed rows and finalized rows whose dashboard status is `COMPLETED` or `INVOICED`, where finalization is an invoice/pro-forma printed flag or an eligible no-invoice closure. Because Business Gifts do not use the Tuesday Dashboard completion flow, an invoiced Business Gift is also excluded from `open` as soon as its real invoice is generated, regardless of dashboard status. The unfiltered All Orders query continues to return it. `complete` / `completed` uses the imported legacy closed flag, and `to-invoice` means `dashboard_status = COMPLETED` with the legacy closed flag false and no invoice/pro-forma/no-invoice finalization yet. This deliberately includes completed `invoice_required = false` jobs until Close Order is confirmed. Search covers job/source/order/invoice numbers, customers, customer codes, contacts, email, client refs, product codes/descriptions, design refs, PSG/stitch source text, imported/profile/saved delivery and invoice addresses, and postcodes. Numeric job/source/invoice fields are included only for digits-only searches. Related line, design, address, contact, and profile matches are calculated as one-time job/customer match sets rather than correlated once per job; imported and saved customer-address matching uses the stored `address_line1` through `address_line5` and `postcode` columns. Line-item and design counts are aggregated only for the requested page. The list response also includes imported order flags and timestamps used by the legacy outstanding-orders grid, plus a normalized `dashboardStatusColors` map copied from the Tuesday Dashboard `STATUS` settings.
- `GET /api/database/outstanding-counts`: returns home-panel open order counts grouped as Printing, Embroidery, and Business Gifts using the same `order_type`/`order_type_abbr` category rules as the legacy UI. Jobs whose normalized Tuesday Dashboard status is `COMPLETED` or `INVOICED` are excluded immediately, whether or not they have been invoiced or otherwise financially finalized. Invoiced Business Gifts are also excluded without requiring either final dashboard status.
- `GET /api/database/status-updates?limit=`: returns the newest durable DB-backed Tuesday Dashboard activity for the DATABASE home feed and Logs page, ordered by event time and event id descending. The default limit is 100 and the maximum is 250. Each row includes an event type, current customer/job identity, order/source identity, job-owner fields, previous/new status where applicable, event time, and display color. Dashboard status changes use their configured Tuesday Dashboard status color, approval events use the dashboard approval green, and invoice-action events use the dashboard invoiced pink. Dashboard-only private jobs are omitted because they do not belong to DATABASE.
- `GET /api/database/visuals?q=&limit=&offset=`: returns Cloudinary-backed Tuesday Dashboard `PROOF`/visible `VISUAL` file attachments joined to their DATABASE jobs, newest attachment first. The default page size is 30 and the maximum is 50; the endpoint uses one-row lookahead `hasMore`/`nextOffset` pagination rather than a total-count query. Search covers previous job/source numbers, customer, job title, visual filename/public id, screen/PSG source text, and `database_job_positions.design_ref`.
- `GET /api/database/visuals/open-jobs`: returns eligible Printing, Embroidery, and Print + Emb jobs for the Visuals fullscreen-modal dropdown and excludes Business Gifts, archived dashboard rows, legacy-complete jobs, and every job whose resolved Tuesday Dashboard group or status is `COMPLETED` even when financial finalization has not happened yet. Each row includes its resolved dashboard group id/title/color/order metadata, and the response is ordered by the persisted Tuesday Dashboard group order followed by newest order number within each group.
- `POST /api/database/visuals/:fileId/attach`: accepts `{ "source_order_id": ... }`, verifies the source is an attached Tuesday Dashboard `PROOF`/visible `VISUAL` file and the target is an eligible open Printing, Embroidery, or Print + Emb job, then adds the existing Cloudinary `public_id`/delivery metadata to that target's standard `PROOF` column without re-uploading the asset. Re-selecting a job that already references the asset is idempotent. The target file then appears in both its Tuesday Dashboard `VISUAL` cell and DATABASE order `VISUAL` tab; shared-asset deletion remains reference-safe.
- `GET /api/database/customers?q=`: returns distinct customers from `database_jobs` plus manual customer-only rows from `database_customer_profiles` in alphabetical order, with each customer's latest order number, latest job title, latest order date, contact, customer code, and order count when orders exist.
- `GET /api/database/users`: returns registered Hub users and a `canManageUsers` capability flag. Pending signup requests are also returned only for user managers. Password hashes and reviewed requests are never included.
- `POST /api/database/signup-requests/:id/accept`: requires user-management permission, locks a pending request, creates the non-manager `hub_users` row with its existing scrypt hash, records the authenticated reviewer, and removes the request hash in one transaction.
- `POST /api/database/signup-requests/:id/reject`: requires user-management permission, rejects a pending request, records the authenticated reviewer, and removes its stored password hash without creating a user.
- `DELETE /api/database/users/:id`: requires user-management permission and cannot delete the current reviewer account. It deletes another `hub_users` row; matching `hub_sessions` rows are removed by the existing `ON DELETE CASCADE` relationship.
- `GET /api/database/customers/:key`: returns one DATABASE customer aggregate. `:key` is either a numeric imported `customer_id`, `name:<customer name>` for rows without a source customer id, or `profile:<id>` for manual customer-only profile rows. The response includes all imported jobs for the customer, customer overview metrics for the stats header, stored/imported contact rows from `database_customer_contacts` merged with job/profile contact fields, imported customer addresses from `database_customer_addresses`, unlimited customer-owned rows from `database_customer_saved_addresses`, manual job/profile invoice/delivery address text as a fallback, per-role default flags, and one design-number row per associated order/job. Design numbers from `database_job_positions.design_ref` and PSG / Stitch Count references found in order, position, or line-item description text are merged onto that single job row. PSG references are normalized with optional suffix letters, stitch counts are normalized from `ST`/`STS`/`STC`/stitch labels or a bare count immediately after a PSG reference, and both are removed from the displayed design-number text so they are not duplicated across columns.
- `PUT /api/database/customers/:key/account-manager`: updates the aggregate customer's account manager by writing `database_jobs.order_owner_user_id`, `order_owner_name`, and `updated_at_source` across the customer's imported/manual job rows, or `database_customer_profiles.account_manager_*` fields for `profile:<id>` customers. The route accepts a Hub `user_id` selected from `/api/database/users`, with a name fallback for legacy/display-only values.
- `POST /api/database/customers`: creates a manual customer-only profile in `database_customer_profiles` from the legacy New Customer form. The route stores customer name/code, contact name, tel/mobile/email, invoice/delivery address line fields and postcode, and the selected/current Hub user as account manager. Created profiles use `profile:<id>` customer keys and do not create synthetic orders in `database_jobs`.
- `POST /api/database/customers/:key/contacts`: creates a stored contact row in `database_customer_contacts` for an imported/customer-name/profile customer. It records title, firstname, lastname, tel, fax, mobile, email, free-text address, source customer/profile link, and Hub creator/updater metadata. The UI deliberately does not expose the legacy `ynMailout`/Marketing control.
- `PUT /api/database/customers/:key/contacts/:contactId`: updates an existing `database_customer_contacts` row after verifying it belongs to the selected customer aggregate.

### Ralawise Catalogue Import

- Source files use `Sku Code` as the canonical and unique supplier-variant identity. `Style Code + Colour Code + Size Code` is not treated as unique. Blank Size Code is accepted when Size Name is present.
- `CustomerDataFull.csv` is streamed through an RFC-capable parser with UTF-8 BOM, quoted comma, embedded-newline, and vendor literal-quote support. The roughly 197 MB file is local/external input and is gitignored; it is not loaded through `xlsx`, split by physical lines, downloaded, or committed.
- The importer requires an explicit path and exactly one mode. `--dry-run` reads the CSV and existing product/catalogue keys but makes no schema, import-run, or product writes. `--apply` additionally requires `--confirm-write`, prints the resolved database hostname/database before writing, uses batches and an advisory lock, and upserts without deletion.
- Parent matching compares whitespace/case-normalized existing `style_code` and `alt_style_code` against Ralawise Style Code and Manufacturer Style Code without filtering on the existing supplier label. The parent must have one unique catalogue candidate. Audited legacy aliases are explicit by Access `style_id`: `959 -> GD005`, `1155 -> J599M`, `1179 -> PR150`, `1349 -> KK350`, `1372 -> GD005`, `1418 -> JH001`, `1472 -> WM101`, `1531 -> GD001`, `2563 -> GD01B`, `2662 -> R200X`, `2766 -> R207X`, `2795 -> J266M`, `3587 -> RX101`, `3595 -> R903X`, and `3677 -> RX402`.
- Within a unique direct parent, colour and size names first use trimmed case-insensitive exact matching, then punctuation/spacing-normalized matching. Reviewed parent aliases may additionally use audited legacy colour/size normalization and the supplier Size Code where the Ralawise display Size Name differs. One unique Live SKU is preferred over duplicate Discontinued candidates; multiple Live candidates or ambiguous parents remain unlinked and are included in the report. Access style 3670 (`PW265` rain jacket) and 3671 (`PW261` winter jacket) are explicit rejections because those same current catalogue codes identify different garments.
- Catalogue imports preserve Carton, Pack, and Single prices. A uniquely matched `database_products.unit_cost` is updated only from a nonblank Carton Price and compared as a decimal, never floating point; blank Carton Price preserves the existing cost.
- Existing positive Access identifiers never change. Access styles 959 and 1372 are equivalent GD005 parents and retain their own existing IDs/rows; new catalogue-only GD005 variants use canonical style 959. Catalogue styles that cannot reuse one unambiguous Access `style_id` receive a persisted negative `database_product_style_id`; catalogue variants receive persisted negative `database_product_source_id` values. Allocations are collision-protected by database uniqueness, assigned under the import lock, reused on repeat imports, and never recalculated from CSV row order.
- Catalogue-only product rows use `supplier_name = Ralawise`, the established Ralawise supplier code when one exists, exact catalogue identity links, Carton Price as unit cost, explicit Live/Discontinued active state, and `stock = NULL` because the CSV is not live inventory. Existing non-matches are untouched.
- No importer path deletes a product or catalogue row because it is missing from a later Ralawise file. Live rows are active and Discontinued rows are retained inactive. Original HTTPS image URLs are stored only as metadata; image bytes are never downloaded or proxied. The vendor literal `Not available` is normalized to a missing URL for active style/variant APIs.

## Supplier API Integrations

- PenCarrie calls use HTTPS `POST` form requests to the configured official `/gateway` endpoint. `pcgetstock` is available through the server-side client. PenCarrie authorizes the configured customer code only when the request originates from a fixed IPv4 address that PenCarrie has associated with that code; `PENCARRIE_STATIC_IP` is diagnostic metadata and cannot force the runtime to use that address.
- Ralawise inventory calls use `POST /v1/login` with top-level `user` and `password` JSON fields, cache the returned JWT until shortly before expiry, and send it as a bearer token to `GET /v1/inventory/:identifier`. The Ralawise user must separately be enabled for API access by Ralawise.
- Ralawise shop calls use a separate server-side session against `shop.ralawise.com`: load the anti-forgery token/cookies, sign in through `/Services/Authentication/SignIn`, snapshot `/services/cart/get`, add grouped exact variant SKUs through `/services/cart/AddMultiItemsToCart`, and apply or update the 15-character customer-name line reference and quantities through `/services/cart/updateBasket` where required. A DATABASE basket update first exact-compares the live referenced rows with its stored audit, modifies only those referenced rows, and exact-compares the final read-back with the desired saved Order Items. Adding or updating the basket does not place/checkout a supplier order. Placed-order confirmation uses `POST /services/orderhistoryservice/searchorders`, then loads the returned order-detail page and parses the exact supplier SKU, stored line reference, quantity, and discounted unit price.
- Supplier credentials, JWTs, and shop cookies remain server-side. The authenticated Hub API exposes only scoped Stock Ordering basket and placed-order sync actions; it never returns credentials/session material to the browser.
