# Ultimate Hub Service Contract

Last reviewed: 2026-08-06

## Purpose

Ultimate Hub is a Node/Express service backed by Railway Postgres. Its production surfaces are the Tuesday Dashboard, the full DATABASE order/customer workflow, Hub authentication, signed scanner flows, and Cloudinary-backed dashboard files.

Production data boundaries:

1. Tuesday Dashboard jobs, status, priority, approvals, dates, designs, line items, and scan state come from Railway Postgres.
2. Dashboard file metadata is stored in Railway Postgres; file bytes are delivered by Cloudinary.
3. Label printing reads the DB-backed Tuesday board payload, prepares status through the DB-backed label endpoint, and renders job, customer, and title text without a QR or other scannable code.
4. DATABASE orders and historical snapshots are populated from MDB snapshots and manual DATABASE entries. The normalized Ralawise catalogue is the source of truth for active stock-product search and colour/size selection; legacy Access product/order IDs remain immutable historical references.
5. The running service has no external work-management OAuth, API client, webhook, board-sync, asset-proxy, or status-write connection.

## Entry Points

- Runtime entry: `server.js`, which loads `server.modular.js`.
- App composition: `src/app.js`.
- Static frontend: `public/`.
- Browser entry pages advertise theme-aware PNG favicons: the black Ultimate icon is selected for light browser themes and the white Ultimate icon is selected for dark browser themes.
- Hub auth: `/login` and `/signup` serve the app login/signup page. `/` and `/index.html` require a Hub session. Full-access users may use DATABASE, Tuesday Dashboard, and `/database-job.html`; `dtf_only` users are restricted to DTF Uploader and its owned upload APIs. The signed public `/test-scan` label endpoint remains unauthenticated.
- Ultimate Hub has three top-level tabs: DATABASE, Tuesday Dashboard, and DTF Uploader. Tuesday Dashboard is the default for full users; DTF Uploader is forced for `dtf_only` users. The active tab is stored in browser localStorage unless a matching `?tab=` value or hash explicitly selects one. DATABASE also stores its current in-app view in browser localStorage, including Lami DTF, the active order/customer tab, and selected order/customer where applicable.
- DB bootstrap: `src/db/migrate.js`.
- Config: `src/config/env.js`.

## API Endpoints

### Ultimate Hub Auth

- `GET /login`: serves the Hub login/signup page in login mode.
- `GET /signup`: serves the same page in signup mode.
- `GET /api/auth/me`: returns `{ user }` for the current Hub session, or `null`; authenticated users include `access_scope` as `full` or `dtf_only`.
- `POST /api/auth/signup`: accepts a signup request for any syntactically valid email address. It validates the submitted name and password, stores a scrypt password hash in `hub_signup_requests`, returns HTTP 202 with `Your request has been received.`, and does not create a user or session. A repeated pending or rejected request for the same email refreshes that request; a request matching an existing user receives the same generic response without changing that user.
- `POST /api/auth/login`: verifies email/password against `hub_users` and starts a session. Pending and rejected signup requests are not users and cannot log in; all `hub_users` rows that existed before the request workflow remain active without requiring review.
- `POST /api/auth/logout`: deletes the current session and clears the cookie.

Security rules:

- Passwords are stored only as Node `crypto.scrypt` hashes with per-user random salts.
- New signup passwords must be 12-128 characters, cannot be highly predictable, and cannot contain the submitted name or email identity. Signup never stores or returns plaintext passwords.
- Signup and login requests have per-IP/account rate limits. Login uses the same generic invalid-credentials response and performs a dummy scrypt verification for unknown users to reduce account-enumeration timing differences.
- Signup responses do not reveal whether an email already has an account or request. Only authenticated users with `hub_users.can_manage_users = true` can read, accept, or reject pending requests through the protected DATABASE API. The migration grants this permission to existing users; accounts created through the request workflow default to false and cannot administer other users.
- Accepting a pending request transactionally inserts it into `hub_users`; the DATABASE reviewer chooses ordinary `full` access with Accept or uploader-only `dtf_only` access with Lami DTF. Rejecting it leaves no login-capable user. Both decisions immediately erase the request's stored password hash and record reviewer audit metadata.
- Session cookies are `HttpOnly`, `SameSite=Lax`, and `Secure` in production/HTTPS.
- Database session rows store only a SHA-256 hash of the random browser session token.

### Health And Status

- `GET /health`: returns `{ ok: true }`.
- `GET /api/status`: returns `{ ok: true, hubAuthenticated: boolean }`.

### DTF Uploader

- `POST /api/dtf/jobs`: creates a DTF job plus 1-40 expected PDF file rows for the logged-in user. Each file is limited to 250MB and quantity 1-99. The server calculates £14.00 net per sheet plus 20% VAT in integer pence and allocates a concurrency-safe `DTF-000001` style number.
- `POST /api/dtf/uploads/sign`: verifies ownership of an expected file, marks it uploading, and returns a short-lived signed Cloudinary `image/authenticated` upload payload for the exact `ultimate-hub/dtf/{userId}/{jobId}/{fileId}` public id.
- `POST /api/dtf/uploads/finalize`: ignores browser URLs and verifies the exact asset through Cloudinary. A valid file must be an authenticated PDF image resource, 1-250MB, with exactly one page whose positive width is no more than 550mm and whose length is 900-1100mm; the three-point PDF metadata tolerance remains at the maximum-width and minimum/maximum-length boundaries. Invalid or failed assets are destroyed and the file/job becomes failed; all verified files move the job to received.
- `POST /api/dtf/layouts/eps-preview`: accepts an authenticated user's EPS file up to 25MB, converts it temporarily through Cloudinary to lossless 300-DPI PNG, returns that PNG, and destroys the temporary asset.
- `GET /api/dtf/files/:fileId`: authorizes the submitting owner or any full user and redirects to a five-minute signed Cloudinary PDF. `?download=1` requests attachment disposition for the Lami DTF Download PDF action; without it the admin Open PDF action previews the same verified premade or generated gang sheet.
- `GET /api/dtf/admin/jobs` and `GET /api/dtf/admin/jobs/:jobId`: full-user-only paginated DTF job summaries and file details for the DATABASE Lami DTF page.
- `PATCH /api/dtf/admin/jobs/:jobId`: full-user-only transition to RECEIVED, IN_PRODUCTION, COMPLETED, or FAILED with updater/timestamp audit fields.
- Job creation is limited to 20, sign/finalize calls to 240 each, and EPS conversions to 30 per user per 15 minutes through Postgres-backed rate-limit buckets.

DTF UI rules:

- DTF Uploader contains only the UltimateHub shell plus Upload Gang/Create Gang modes; the standalone BRAND header, home, profile, login, and customer history are not ported. Upload mode shows the page title without supporting copy, and its upload card ends after the PDF list so pricing and submission actions sit directly beneath it; layout creation remains available from the Create Gang mode tab.
- Premade sheets are browser-validated with PDF.js before job creation using the same one-page, maximum-550mm-width, and 900-1100mm-length rule as server finalization. Multiple PDFs and quantities may be combined in one job, previewed individually, and persisted as unsent per-user IndexedDB drafts. The upload preview has no separate Preview/filename heading and grows to the full rendered sheet height without an internal scrollbar. Valid file rows omit the green size-confirmation line and file-size text while checking and error text remain visible; the quantity controls and delete X sit beneath the full-width wrapping filename. The empty upload icon/instructions are centered as an overlay inside the preview window and are hidden when its PDF canvas is shown. The upload card begins with `Add gang sheet PDFs` without an extra arrow icon. The headline price shows the net subtotal followed by smaller purple `+ VAT`; the existing Sheets, Subtotal, VAT, and Total breakdown remains below in black. Files over 100MB use Cloudinary's signed REST chunk protocol with contiguous 20MB ranges, a per-file upload id, and progress after every chunk so the advertised 250MB ceiling does not depend on the ordinary request-size limit.
- The layout editor accepts PNG, EPS, and one-page PDF artwork on a fixed 550 × 1000mm sheet. New artwork retains its source physical dimensions: PNG uses its pHYs resolution or a 300-DPI print fallback, EPS uses its HiResBoundingBox/BoundingBox or the 300-DPI preview fallback, and PDF uses the one-page media size. Oversized source artwork is rejected instead of normalized. Background and Artwork gap controls share the first row with a thin purple divider; the gap uses the same purple heading style, and each light/grey/dark selector visually mirrors its canvas background. The artwork-gap stepper is compact and keeps `mm` directly beside its number. The artwork action reads `Upload PNG, EPS or PDF`, and the canvas panel has no separate Preview heading or dimensions pill. The editor supports a 0-250mm gap (10mm default), light/grey/dark backgrounds, keyboard-editable proportional W/H controls, copies, group/individual 90-degree rotation, selection/z-order, deletion, dragging, and automatic non-overlapping packing capped at 80 pieces. Automatic packing fills each available row from left to right before wrapping down to the next row. The canvas artwork prompt is shown only while the layout is empty, including while an initial EPS is being processed, and hides as soon as the first artwork is accepted. EPS conversion displays a blocking loading wheel over the canvas until processing succeeds or fails.
- Generated PDFs use `pdf-lib`: PNG bytes and one-page PDF artwork are embedded independently without whole-sheet rasterization; EPS uses the returned 300-DPI PNG. The output is one exact 550 × 1000mm PDF page and is added back to the upload draft.
- DATABASE home exposes a blue Lami DTF button. Its admin view shows job number/date/customer/email, files, sheet quantity, subtotal, VAT, total, status, per-file upload detail, signed PDF links, and the status control.

### Tuesday Dashboard

- `GET /api/test-dashboard/board`: returns the Tuesday Dashboard payload from Railway/Postgres `database_jobs`, `database_job_line_items`, `database_job_positions`, `job_scans`, and test-dashboard state/file tables. File values contain Cloudinary `secure_url` metadata only.
- `PUT /api/test-dashboard/items/:jobId/status-column`: updates DB-backed or private dashboard `STATUS` / `PRIORITY` state. Body is `{ "columnId": "...", "label": "..." }`, or `{ "columnId": "...", "clear": true }` for clearing `PRIORITY`. DB-backed rows write `test_dashboard_job_state` and `database_jobs.dashboard_status` / `dashboard_priority`; private rows write only `test_dashboard_private_jobs`. The route applies local status-driven group moves, completed cleanup, invoiced archive, and priority clearing. `PRE-PRODUCTION` is not selectable in STATUS; the group remains reachable through job approval / `NO STOCK`. `AWAITING APPROVAL` uses the ordinary `#2b2b2c` dashboard background with white text. A Print + Emb job cannot be changed to `READY TO PRINT` until both `TRANS` and `JAQ` are checked; the API returns `split_job_ticks_required` plus the missing tick names without changing status. `STATUS = COMPLETED` normally moves to COMPLETED; for an active Print + Emb split, the virtual Print and Embroidery row ids store independent dashboard-only branch statuses and the aggregate `database_jobs.dashboard_status` remains `READY TO PRINT` until both branches are complete. The first completed branch stays in its production group; the second completion atomically removes the split state, restores the one canonical dashboard row, and moves it to COMPLETED. `STOCK ORDERED` preserves the current non-production group until approval; `TO SAMPLE` moves to TO SAMPLE; and `SAMPLED` moves to OFFICE. `database_jobs.is_complete` remains the imported closed/invoiced flag and is not set merely by dashboard `COMPLETED`.
- `POST /api/test-dashboard/private-jobs`: creates a dashboard-only private job row in `test_dashboard_private_jobs`, usually in OFFICE. These rows are not `database_jobs`, do not allocate job/order/invoice numbers, and do not appear in DATABASE.
- `DELETE /api/test-dashboard/private-jobs/:jobId`: permanently deletes a dashboard-only private job row and rejects normal DB-backed ids. Any Cloudinary proof/design assets referenced by the private row are queued for deletion best-effort.
- `PUT /api/test-dashboard/items/:jobId/name`: renames dashboard-only private jobs. It rejects DB-backed job ids because real order titles stay owned by DATABASE.
- `PUT /api/test-dashboard/items/:jobId/group`: moves a DB-backed or private Tuesday Dashboard row to HOLD, OFFICE, or PRE-PRODUCTION from the row action menu. Moving to PRE-PRODUCTION requires `JOB ✔` approval; unapproved rows are rejected and continue to resolve to OFFICE unless explicitly moved to HOLD. It writes the matching dashboard status label (`HOLD`, `AWAITING APPROVAL`, or `NO STOCK`), except that a row already at `CHECKED IN` retains that status when moved to PRE-PRODUCTION, and updates `database_jobs.dashboard_status` only for DB-backed jobs.
- `PUT /api/test-dashboard/items/:jobId/date-column`: updates the dashboard `DATE` column for DB-backed or private Tuesday Dashboard rows and recalculates `PRIORITY` from the due date (`Critical`, `High`, `Medium`, `Low`). DB-backed jobs with `database_jobs.customer_date_required` keep the DATABASE customer date and reject dashboard date edits.
- `PUT /api/test-dashboard/items/:jobId/checkbox-column`: updates Tuesday Dashboard parent checkbox columns for DB-backed rows in `test_dashboard_job_state.column_values` or private rows in `test_dashboard_private_jobs.column_values`. Body is `{ "columnId": "...", "checked": true|false }`. The route accepts only configured checkbox columns. The `JOB ✔` checkbox is the job-approved flag and is the main driver for whether a job is approved/readiness-approved; DB-backed approval is stored on `database_jobs.proof_approved` / `proof_approved_at`, while private approval stays dashboard-only. Checking `JOB ✔` requires at least one design/PSG reference and at least one file in the Tuesday Dashboard `PROOF` column; otherwise the route returns `approval_requirements_missing`. Successful approval moves the job to PRE-PRODUCTION, preserves `STATUS = STOCK ORDERED` or `CHECKED IN` when either status is already set and otherwise sets `STATUS = NO STOCK`, clears `PRIORITY`, and sets `DATE` to 14 calendar days from approval. Clearing `JOB ✔` returns the job to OFFICE / `AWAITING APPROVAL`, clears priority, and clears date unless a DB-backed customer date is required.
- `PUT /api/test-dashboard/items/:jobId/text-column`: updates the DB-backed Tuesday Dashboard `NOTES` parent text column in `test_dashboard_job_state.column_values`. Body: `{ "columnId": "...", "value": "..." }`. The route accepts only the mirrored `NOTES` text/long-text column so DES/PSG remains on its design reconciliation route.
- `PUT /api/test-dashboard/items/:jobId/design-column`: reconciles DES/PSG values edited from the Tuesday Dashboard with the related DATABASE Design tab rows. Body: `{ "columnId": "...", "value": "..." }`. Submitted values are split on `/`; each represented design/PSG reference is matched against existing `database_job_positions.design_ref` values. Exact matches are kept, changed refs update an existing row of the same kind where possible, new refs insert rows, and removed refs delete dashboard-created empty rows or clear `design_ref` on rows that still have position/colour data. Exact represented design/PSG references are not inserted twice.
- `GET /api/test-dashboard/scan-url?jobId=...`: returns a signed `/test-scan?j=...&ts=...&sig=...` URL for the serial scanner workflow.
- `POST /api/test-dashboard/items/:jobId/label-printed`: prepares a Tuesday Dashboard label-print event without generating or returning a scanner URL. The event normally sets `STATUS = CHECKED IN` in test-dashboard state and `database_jobs.dashboard_status` while preserving the current group and job-approval state; `CHECKED IN` is an explicit unapproved-status override and is not replaced by `AWAITING APPROVAL`. Reprinting never regresses `COMPLETED`; it also preserves `READY TO PRINT` when the job's resolved group is no longer PRE-PRODUCTION. The label is still prepared and printed when either status is preserved. Private Tuesday Dashboard rows receive the same dashboard-only status automation.
- `GET /test-scan?j=...&ts=...&sig=...`: public signed scan endpoint for DB-backed labels. It records Railway scanner state against the job source order id and updates `test_dashboard_job_state` plus `database_jobs.dashboard_status`.
- `POST /api/test-dashboard/scanner`: accepts Tuesday scan URLs or bare numeric DB job ids, records scan state, and refreshes DB-backed status/check-in state.
- `POST /api/test-dashboard/uploads/signature`: returns a short-lived signed Cloudinary browser-upload payload. It requires `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and `CLOUDINARY_API_SECRET`; the API secret never reaches the browser. The signed params are limited to Cloudinary upload params that Cloudinary includes in its signature check; PDF delivery handling is done after upload from the original filename and saved metadata. Requests for the underlying `PROOF`/visible `VISUAL` column are rejected unless the filename ends in `.pdf`, `.jpg`, `.jpeg`, or `.png`. The Tuesday Dashboard file cells and DATABASE order `VISUAL` tab share this endpoint; a real `database_jobs` row is sufficient, so Business Gifts can receive stored visuals without acquiring Tuesday Dashboard identity.
- `POST /api/test-dashboard/items/:jobId/files`: saves Cloudinary upload metadata for a DB job/file column in `test_dashboard_files`. For the underlying `PROOF`/visible `VISUAL` column, it also requires the original filename and Cloudinary format to resolve to PDF, JPEG, or PNG, preventing unsupported metadata from bypassing the signature-stage check. DATABASE order-tab uploads write through this same metadata path, including for Business Gifts; non-gift jobs already represented on Tuesday Dashboard therefore show the new file in the dashboard `VISUAL` cell, while gift orders remain absent from the board and retain the file for DATABASE storage/viewing.
- `DELETE /api/test-dashboard/items/:jobId/proof-files`: removes all files from the Tuesday Dashboard `PROOF` column for a DB-backed or private row. DB-backed rows delete matching `test_dashboard_files` metadata; private rows clear the proof payload from `test_dashboard_private_jobs`; Cloudinary assets are destroyed best-effort.
- `DELETE /api/test-dashboard/items/:jobId/files/:fileId`: deletes one test-dashboard file from a DB-backed or dashboard-only private job and best-effort destroys the Cloudinary asset.

### Scanner

- New labels contain no QR or other generated scanner code. `/api/test-dashboard/scan-url` and the public signed `/test-scan` endpoint remain available for the serial scanner workflow and previously printed signed labels.
- The browser serial connection posts only to `/api/test-dashboard/scanner`.
- `job_scans` and `job_scan_events` are the scan source of truth.

The one desktop exception is `Ultimate Packing`, whose packing-only `LABEL` column comes first, followed by the same job-number column. The job-number column is 64px wide on desktop and 72px on mobile/phone-landscape so five-digit order numbers containing wide digits remain fully visible. The job-number control uses the DATABASE outer-background light blue (`#8ec7e3`) and opens the matching DATABASE order by `database_jobs.source_order_id`. The title cell contains the customer name as a smaller uppercase eyebrow above the job title, coloured with the row's group accent, while the job number and separating dash remain excluded. Standalone `LIMITED` and `LTD` words are omitted case-insensitively from this displayed customer eyebrow only. On mobile and phone landscape, tapping the job-title cell opens a dashboard-styled job overview dialog showing the same cleaned customer and job title, DES/PSG design numbers, summed garment quantity, and a line-item disclosure that starts closed. The dialog header shows only the same light-blue linked job number, which opens the same DATABASE order info page. Expanding the disclosure shows every dashboard garment line with code, colour, size, and quantity. A full-width colour-coded status band stays at the bottom of the dialog and opens the existing STATUS picker, including the existing COMPLETED confirmation and status automation.

Parent grids use their exact calculated track width rather than stretching to the widest group, and the final parent header/cell keeps its right border, so the last `FILES` column ends cleanly without a trailing dark row area. Clicking a file icon opens that proof in the shared file/PDF viewer with the normal multi-file and PDF-page navigation. On touch layouts, PDF canvases and image previews support two-finger pinch zoom plus one-finger panning/swiping while enlarged; the viewer rerenders PDFs at the settled zoom for clarity.

Expanded subitem grids start with `CODE`, followed by a display-only `BRAND` column resolved in order from the line item's linked normalized Ralawise catalogue style, its legacy style mapping, and finally the explicitly audited legacy-to-current product-style aliases; followed by `Subitem` and the remaining existing columns. Dashboard candidates include legacy-open jobs plus jobs with DB identity from `database_jobs.dashboard_status` / `dashboard_priority`, scanner status, or any non-archived `test_dashboard_job_state` row. - Tuesday Dashboard parent rows render a client-only `TOTAL` column immediately to the right of the `JOB TITLE` column. Editing an existing displayed ref updates its existing DATABASE row where possible; deleting a displayed ref removes dashboard-created empty rows or clears the `design_ref` from rows that still contain position/colour data. The Tuesday Dashboard `NOTES` parent cell is an inline text input that saves on Enter/blur through `/api/test-dashboard/items/:jobId/text-column` into `test_dashboard_job_state`.

Every page contains the job number, customer, and job title followed by its centred `1 of 3`, `2 of 3`, etc. count; no QR is generated or printed. ### DATABASE

The dashboard has a `DATABASE` tab backed by a full-history MDB import.

Frontend files:

- `public/index.html`: sidebar tab and legacy-style DATABASE hub markup.
- `public/database.js`: DATABASE home screen, manual new-order form, outstanding order grouping, order navigation, order detail tabs, line-item rendering, and design-position rendering.
- `public/database-job.html`: older direct full-width job info page retained as a fallback.
- `public/database-job.js`: older job facts, contact fields, line items, and positions rendering for the fallback page.
- `public/styles.css`: scoped legacy DATABASE hub styles plus older fallback page table styles.

Backend files:

- `src/routes/database.js`: `/api/database` JSON endpoints.
- `src/db/databaseSchema.js`: idempotent table creation.
- `scripts/import-database-mdb.js`: imports `PS_XP_tab.mdb` into Railway/Postgres, including a products-only mode for the full Access product catalogue.

Endpoints:

- `GET /api/database/summary`: returns counts for jobs, line items, positions, products, customer addresses, customer contacts, import status, counts by year, and counts by type.
- `GET /api/database/reports?range=daily|weekly|monthly|mtd|ytd|last12|custom-month|custom-year`: returns the DATABASE Analytics & Reports financial payload using job order date with source-created date fallback and Europe/London period boundaries. Daily means today with hourly graph buckets; weekly is the trailing 7 days with daily buckets; monthly is the trailing 30 days with daily buckets; month-to-date uses daily buckets; year-to-date uses monthly buckets and accepts an optional validated `year=YYYY`; and last12 is the rolling 12 calendar months with monthly buckets. `custom-month` requires `period=YYYY-MM` and returns that complete calendar month in daily buckets, while `custom-year` requires `period=YYYY` and returns that complete calendar year in monthly buckets. Missing graph buckets are returned as zero. Financial values use non-internal invoiceable line items: net sales are `quantity * unit_price`, VAT follows the invoice child/youth zero-rating rules and otherwise normalizes stored decimal/percentage VAT rates, gross sales are net plus VAT, COGS are `quantity * unit_cost`, and gross profit/margin are net sales less COGS so VAT does not inflate profit. The response includes totals, average order value, units, missing price/cost coverage counts, capped top-five customers, sales by order type, the highest-grossing order, the available order years used by the report selectors, and every order in the selected period with order/customer/job identity plus gross sales, net sales, COGS, and gross profit.
- `GET /api/database/jobs?q=&customer=&type=&year=&status=&limit=&offset=&includeTotal=`: returns paginated jobs. Default and UI page size is 100 jobs. `includeTotal=false` skips the count query and returns `hasMore` from a one-row lookahead; the All Orders UI uses that path for active searches and follow-up page loads so it does not execute the broad search twice before showing the first page. Supported `status` filters include `open`, `complete` / `completed`, and `to-invoice`; `open` excludes legacy-closed rows and finalized rows whose dashboard status is `COMPLETED` or `INVOICED`, where finalization is an invoice/pro-forma printed flag or an eligible no-invoice closure. Because Business Gifts do not use the Tuesday Dashboard completion flow, an invoiced Business Gift is also excluded from `open` as soon as its real invoice is generated, regardless of dashboard status. The unfiltered All Orders query continues to return it. `complete` / `completed` uses the imported legacy closed flag, and `to-invoice` means `dashboard_status = COMPLETED` with the legacy closed flag false and no invoice/pro-forma/no-invoice finalization yet. This deliberately includes completed `invoice_required = false` jobs until Close Order is confirmed. Search covers job/source/order/invoice numbers, customers, customer codes, contacts, email, client refs, product codes/descriptions, design refs, PSG/stitch source text, delivery/invoice addresses, and postcodes. Numeric job/source/invoice fields are included only for digits-only searches. Related line, design, address, contact, and profile matches are calculated as one-time job/customer match sets rather than correlated once per job; imported customer-address matching uses the stored `address_line1` through `address_line5` and `postcode` columns. Line-item and design counts are aggregated only for the requested page. The list response also includes imported order flags and timestamps used by the legacy outstanding-orders grid, plus a normalized `dashboardStatusColors` map copied from the Tuesday Dashboard `STATUS` settings.
- `GET /api/database/outstanding-counts`: returns home-panel open order counts grouped as Printing, Embroidery, and Business Gifts using the same `order_type`/`order_type_abbr` category rules as the legacy UI. Jobs whose normalized Tuesday Dashboard status is `COMPLETED` or `INVOICED` are excluded immediately, whether or not they have been invoiced or otherwise financially finalized. Invoiced Business Gifts are also excluded without requiring either final dashboard status.
- `GET /api/database/visuals?q=&limit=&offset=`: returns Cloudinary-backed Tuesday Dashboard `PROOF`/visible `VISUAL` file attachments joined to their DATABASE jobs, newest attachment first. The default page size is 30 and the maximum is 50; the endpoint uses one-row lookahead `hasMore`/`nextOffset` pagination rather than a total-count query. Search covers previous job/source numbers, customer, job title, visual filename/public id, screen/PSG source text, and `database_job_positions.design_ref`.
- `GET /api/database/visuals/open-jobs`: returns eligible Printing, Embroidery, and Print + Emb jobs for the Visuals fullscreen-modal dropdown and excludes Business Gifts, archived dashboard rows, legacy-complete jobs, and every job whose resolved Tuesday Dashboard group or status is `COMPLETED` even when financial finalization has not happened yet. Each row includes its resolved dashboard group id/title/color/order metadata, and the response is ordered by the persisted Tuesday Dashboard group order followed by newest order number within each group.
- `POST /api/database/visuals/:fileId/attach`: accepts `{ "source_order_id": ... }`, verifies the source is an attached Tuesday Dashboard `PROOF`/visible `VISUAL` file and the target is an eligible open Printing, Embroidery, or Print + Emb job, then adds the existing Cloudinary `public_id`/delivery metadata to that target's standard `PROOF` column without re-uploading the asset. Re-selecting a job that already references the asset is idempotent. The target file then appears in both its Tuesday Dashboard `VISUAL` cell and DATABASE order `VISUAL` tab; shared-asset deletion remains reference-safe.
- `GET /api/database/customers?q=`: returns distinct customers from `database_jobs` plus manual customer-only rows from `database_customer_profiles` in alphabetical order, with each customer's latest order number, latest job title, latest order date, contact, customer code, and order count when orders exist.
- `GET /api/database/users`: returns registered Hub users and a `canManageUsers` capability flag. Pending signup requests are also returned only for user managers. Password hashes and reviewed requests are never included.
- `POST /api/database/signup-requests/:id/accept`: requires user-management permission, locks a pending request, creates the non-manager `hub_users` row with its existing scrypt hash, records the authenticated reviewer, and removes the request hash in one transaction.
- `POST /api/database/signup-requests/:id/reject`: requires user-management permission, rejects a pending request, records the authenticated reviewer, and removes its stored password hash without creating a user.
- `DELETE /api/database/users/:id`: requires user-management permission and cannot delete the current reviewer account. It deletes another `hub_users` row; matching `hub_sessions` rows are removed by the existing `ON DELETE CASCADE` relationship.
- `GET /api/database/customers/:key`: returns one DATABASE customer aggregate. `:key` is either a numeric imported `customer_id`, `name:<customer name>` for rows without a source customer id, or `profile:<id>` for manual customer-only profile rows. The response includes all imported jobs for the customer, customer overview metrics for the stats header, stored/imported contact rows from `database_customer_contacts` merged with job/profile contact fields, imported customer addresses from `database_customer_addresses` with individual address line fields plus manual job/profile invoice/delivery address text as a fallback, and one design-number row per associated order/job. Design numbers from `database_job_positions.design_ref` and PSG / Stitch Count references found in order, position, or line-item description text are merged onto that single job row. PSG references are normalized with optional suffix letters, stitch counts are normalized from `ST`/`STS`/`STC`/stitch labels or a bare count immediately after a PSG reference, and both are removed from the displayed design-number text so they are not duplicated across columns.
- `PUT /api/database/customers/:key/account-manager`: updates the aggregate customer's account manager by writing `database_jobs.order_owner_user_id`, `order_owner_name`, and `updated_at_source` across the customer's imported/manual job rows, or `database_customer_profiles.account_manager_*` fields for `profile:<id>` customers. The route accepts a Hub `user_id` selected from `/api/database/users`, with a name fallback for legacy/display-only values.
- `POST /api/database/customers`: creates a manual customer-only profile in `database_customer_profiles` from the legacy New Customer form. The route stores customer name/code, contact name, tel/mobile/email, invoice/delivery address line fields and postcode, and the selected/current Hub user as account manager. Created profiles use `profile:<id>` customer keys and do not create synthetic orders in `database_jobs`.
- `POST /api/database/customers/:key/contacts`: creates a stored contact row in `database_customer_contacts` for an imported/customer-name/profile customer. It records title, firstname, lastname, tel, fax, mobile, email, free-text address, source customer/profile link, and Hub creator/updater metadata. The UI deliberately does not expose the legacy `ynMailout`/Marketing control.
- `PUT /api/database/customers/:key/contacts/:contactId`: updates an existing `database_customer_contacts` row after verifying it belongs to the selected customer aggregate.
- `DELETE /api/database/customers/:key/contacts/:contactId`: deletes an existing `database_customer_contacts` row after verifying it belongs to the selected customer aggregate.
- `PUT /api/database/customers/:key/addresses`: updates the selected customer's default invoice and delivery address fields in `database_customer_profiles`, including Address 1-5, Postcode, Tel, and Fax. Imported-only customers get a manual profile row created on first address edit so the customer Addresses tab can persist changes without rewriting historical imported address rows.
- `GET /api/database/customers/search?q=`: searches distinct customer/contact values from `database_jobs` and `database_customer_profiles`, using the same imported/manual customer data that populates outstanding orders and order/customer details.
- `POST /api/database/jobs`: creates a real manual `database_jobs` row from the legacy New Order form. Required fields are the red New Order fields: customer, contact, order type, job title, order date, delivery date, delivery method, payment terms, order taken by, delivery address, invoice address, and invoice required. The route accepts Business Gifts, Printing, Print + Emb, and Embroidery order types, deriving `order_type_abbr` as `G`, `P`, `PE`, or `E`. It allocates the next source order id and next job/order number from `MAX(source_order_id) + 1` and `GREATEST(MAX(order_no), 50000) + 1`. Manual order creation does not allocate or reserve an invoice number; `invoice_no` stays `NULL` until the Invoice action generates the invoice. The route stores selected customer/contact/address ids and address text when provided, marks the row `is_manual_entry = true`, and seeds both `database_jobs.dashboard_status` and `test_dashboard_job_state` `STATUS` as `AWAITING APPROVAL` so new DB-created jobs have Tuesday Dashboard identity and land in OFFICE until approved.
- `POST /api/database/jobs/:id/repeat`: transactionally creates a new manual/reorder job from an existing source-order id or job number. Body must be `{ "copy_line_items": true|false }`. The copy receives fresh source-order and job/order numbers, uses the repeat action time as its new order date/source year, records the acting Hub user as order owner/taken-by user, and copies the source customer/contact/address, order type/title/reference, delivery/payment details, delivery date, comments, screen/PSG source text, design-position rows, and Tuesday Dashboard PROOF/visual file references. Legacy PSG/stitch references found only in a source line description are materialized as design-position references on the new job, so they survive even when line-item copying is declined. The repeat never copies invoice numbers/dates/printed flags, delivery-note state, completion, customer-date priority, bagged/automatic/artwork/screens/shirts workflow flags, proof approval, dashboard priority/type/progress, supplier-order ids, or other completed workflow state; the new job starts unapproved in OFFICE with `STATUS = AWAITING APPROVAL`, just like New Order. When `copy_line_items` is true, every stock, non-stock, non-deliverable, internal, and other stored source line is copied with fresh legacy-compatible line ids and preserved product/type/pricing/VAT data, but every copied `quantity` is `NULL` so quantities are blank for re-entry. When false, no line items are created. Design and proof references are copied in either mode.
- `POST /api/database/jobs/:id/close-without-invoice`: finalizes one job only when `invoice_required = false`, setting `database_jobs.closed_without_invoice = true` without allocating an invoice number or changing invoice date/printed fields. A job at final dashboard status `COMPLETED` or `INVOICED` then leaves To Invoice, Open Orders, and the Tuesday Dashboard through the same final-status-plus-finalization lifecycle used by invoiced jobs. The dedicated state is idempotent and is ignored if the job later requires an invoice.
- `GET /api/database/jobs/:id`: returns one job plus contact fields, line items, position rows, proof files, and `customerOverview` metrics for the selected job's customer. `:id` may be source order id or job number.
- `GET /api/database/stock-ordering`: returns non-gift, non-completed jobs that still need stock ordering and have at least one stock line item; jobs with only non-stock lines are omitted, while jobs with both stock and non-stock lines remain eligible. The payload includes stock and non-stock line items, exact Ralawise variant SKU/catalogue status resolved from the line-level canonical identity first with the linked historical product as fallback, and per-job Ralawise basket eligibility/audit state; non-deliverable/internal lines are excluded. It excludes jobs whose Tuesday Dashboard status or stored group has reached `STOCK ORDERED`, `CHECKED IN`, `READY TO PRINT`, PRINT, EMBROIDERY, COMPLETED, `IN PRODUCTION`, or `INVOICED`.
- `POST /api/database/stock-ordering/mark-ordered`: accepts `{ "sourceOrderIds": [...] }` from the Stock Ordering PDF modal and atomically marks the matching DATABASE jobs and Tuesday Dashboard state rows as `STOCK ORDERED`. The update preserves the current non-production dashboard group, keeps unapproved jobs out of production groups, clears any archived dashboard state for those rows, and returns the updated job ids/status timestamps so the browser can remove them from the Stock Ordering list before opening print/download.
- `POST /api/database/stock-ordering/:id/ralawise-basket`: locks one stock-ordering job, requires every product line to resolve to one exact live Ralawise colour/size SKU, groups repeated SKUs at the correct summed quantity, and attaches the customer name (trimmed to Ralawise's 15-character OL Ref limit) as the supplier line reference, falling back to the job/order number only when the customer name is missing. It writes `adding` audit rows before the external request, first reconciles the exact SKU/reference/quantity against the current Ralawise basket to make retries duplicate-safe, then adds any missing payload through the authenticated Ralawise shop basket. A confirmed/reconciled basket result changes only the durable audit state to `basketed`; it does not change the DATABASE or Tuesday Dashboard job status. Supplier/network failures also leave the job status unchanged. Ralawise allocation shortages are returned and stored as warnings but do not reverse a successful basket addition.
- `POST /api/database/stock-ordering/:id/ralawise-basket/update`: reconciles a previously `basketed`, not-yet-ordered job after its saved Order Items change. Before any mutation it requires the live Ralawise rows under the job's stored OL Ref to exactly match the durable audited SKU/quantity snapshot; a manually changed, missing, or checked-out basket returns HTTP 409 and is left untouched. It then changes/removes the old referenced quantities, adds any replacement SKUs, reapplies the same OL Ref, reads the basket back, and replaces the local line audit only after the resulting referenced SKU/quantity set exactly matches the current saved product lines. Empty current product sets are valid only for this update path so deleting all saved stock lines can clear the job's basket allocation. Concurrent updates are locked and recorded with a durable sync state/revision; unresolved current SKUs and unverified or partially saved results remain visibly retryable and must not be checked out.
- `POST /api/database/stock-ordering/ralawise-sync`: checks `basketed` jobs against authenticated Ralawise placed-order history and detail pages. A job is confirmed only when every audited local line can be quantity-matched by exact SKU and its stored supplier line reference against placed supplier lines. Persisting that exact reference keeps jobs added under the earlier job-number convention compatible with placed-order matching. The same transaction records the supplier order/line metadata, replaces each matched `database_job_line_items.unit_cost` with the returned discounted supplier unit price when present, and then marks the DATABASE job plus Tuesday Dashboard state `STOCK ORDERED`. Partial or missing supplier matches leave the job and its costs unchanged. The Stock Ordering page starts this sync after its initial list renders so supplier history cannot block the page, and a server poller repeats it in the background.
- `PUT /api/database/jobs/:id`: updates supported order-level fields. The current UI uses it for `job_title`, `order_type`, `client_order_no`, and `comments` autosave, order-detail invoice/delivery address dropdown saves, `invoice_required` Yes/No changes, and with `{ "mark_invoiced": true }` when the order-view Invoice action is clicked. Order type updates accept Business Gifts, Printing, Print + Emb, and Embroidery, write the matching `order_type_abbr`, clear stale `dashboard_type` / dashboard TYPE overrides, and let Tuesday Dashboard derive the refreshed TYPE/group from `database_jobs`. The route also accepts selected contact fields and invoice/delivery address ids/text for manual order maintenance. Mutating job routes resolve `:id` to one canonical `database_jobs.source_order_id` first, preferring an exact `source_order_id` match over an `order_no` fallback, then write by that resolved source id only so overlapping source/order numbers cannot update the wrong row. Changing `invoice_required` clears `closed_without_invoice` when the value changes; changing it to false is rejected once `invoice_no` exists or `invoice_printed` is true, so an already-generated invoice cannot be invalidated. The invoice action requires non-Business-Gift jobs to have current Tuesday Dashboard status `COMPLETED`; any other status returns HTTP 409 with `This job is not yet completed` before an invoice number can be allocated. Business Gift orders, identified by their normalized order type or legacy `G` abbreviation, can be invoiced at any dashboard status because they do not use the Tuesday Dashboard workflow. For an eligible job the route allocates an invoice number if missing, sets `invoice_required = true` plus `invoice_printed = true`, and clears any stale `closed_without_invoice` state, but it does not set `is_complete`, `complete_date`, or force `dashboard_status = INVOICED`. It also sets `database_jobs.invoice_date` once on first invoice generation using any supplied manual invoice date, otherwise the existing completion date or current timestamp; later invoice clicks preserve the stored invoice date unless a manual date is explicitly submitted. - `GET /api/database/products/search?field=style|code&q=&preferredStyleId=`: searches Live normalized Ralawise styles/variants directly. Style searches cover style name, brand, Style Code, and Manufacturer Style Code; code searches also cover exact/partial supplier and alpha SKUs. Safely linked positive Access style/alternate codes remain search-only aliases, and style-code matching ignores leading zero-padding in the numeric portion so legacy/operator inputs such as `GD01` and `AT01` resolve to canonical `GD001` and `AT001` parents. A nonblank query ignores the preference and usage ordering and uses normal search relevance. ### Ralawise Catalogue Import

- Source files use `Sku Code` as the canonical and unique supplier-variant identity. `Style Code + Colour Code + Size Code` is not treated as unique. Blank Size Code is accepted when Size Name is present.
- `CustomerDataFull.csv` is streamed through an RFC-capable parser with UTF-8 BOM, quoted comma, embedded-newline, and vendor literal-quote support. The roughly 197 MB file is local/external input and is gitignored; it is not loaded through `xlsx`, split by physical lines, downloaded, or committed.
- The importer requires an explicit path and exactly one mode. `--dry-run` reads the CSV and existing product/catalogue keys but makes no schema, import-run, or product writes. `--apply` additionally requires `--confirm-write`, prints the resolved database hostname/database before writing, uses batches and an advisory lock, and upserts without deletion.
- Parent matching compares whitespace/case-normalized existing `style_code` and `alt_style_code` against Ralawise Style Code and Manufacturer Style Code without filtering on the existing supplier label. The parent must have one unique catalogue candidate. Audited legacy aliases are explicit by Access `style_id`: `959 -> GD005`, `1155 -> J599M`, `1179 -> PR150`, `1349 -> KK350`, `1372 -> GD005`, `1418 -> JH001`, `1472 -> WM101`, `1531 -> GD001`, `2563 -> GD01B`, `2662 -> R200X`, `2766 -> R207X`, `2795 -> J266M`, `3587 -> RX101`, `3595 -> R903X`, and `3677 -> RX402`.
- Within a unique direct parent, colour and size names first use trimmed case-insensitive exact matching, then punctuation/spacing-normalized matching. Reviewed parent aliases may additionally use audited legacy colour/size normalization and the supplier Size Code where the Ralawise display Size Name differs. One unique Live SKU is preferred over duplicate Discontinued candidates; multiple Live candidates or ambiguous parents remain unlinked and are included in the report. Access style 3670 (`PW265` rain jacket) and 3671 (`PW261` winter jacket) are explicit rejections because those same current catalogue codes identify different garments.
- Catalogue imports preserve Carton, Pack, and Single prices. A uniquely matched `database_products.unit_cost` is updated only from a nonblank Carton Price and compared as a decimal, never floating point; blank Carton Price preserves the existing cost.
- Existing positive Access identifiers never change. Access styles 959 and 1372 are equivalent GD005 parents and retain their own existing IDs/rows; new catalogue-only GD005 variants use canonical style 959. Catalogue styles that cannot reuse one unambiguous Access `style_id` receive a persisted negative `database_product_style_id`; catalogue variants receive persisted negative `database_product_source_id` values. Allocations are collision-protected by database uniqueness, assigned under the import lock, reused on repeat imports, and never recalculated from CSV row order.
- Catalogue-only product rows use `supplier_name = Ralawise`, the established Ralawise supplier code when one exists, exact catalogue identity links, Carton Price as unit cost, explicit Live/Discontinued active state, and `stock = NULL` because the CSV is not live inventory. Existing non-matches are untouched.
- No importer path deletes a product or catalogue row because it is missing from a later Ralawise file. Live rows are active and Discontinued rows are retained inactive. Original HTTPS image URLs are stored only as metadata; image bytes are never downloaded or proxied. The vendor literal `Not available` is normalized to a missing URL for active style/variant APIs.

Core source mappings:

- Jobs: `tblOrder` joined to `tblCustomer`, `tblContact`, `tblOrderType`, and `tblStaff`. `tblOrder.ynComplete` imports to `database_jobs.is_complete`; despite the current column name, it is the legacy closed flag, and closed jobs are treated as already invoiced. `tblOrder.TakenByStaffID` joins to `tblStaff.StaffID` and imports the staff display name into `database_jobs.order_taken_by`; `tblOrder.TraceStaffID` remains separate audit metadata in `database_jobs.trace_staff_id` and must not be used as the order taken-by value.
- Manual New Order rows store non-MDB form fields directly on `database_jobs`: `delivery_method`, `payment_terms`, `order_taken_by`, `order_owner_user_id`, `order_owner_name`, `delivery_address`, `invoice_address`, `is_manual_entry`, and the initial Tuesday Dashboard `dashboard_status`.
- Manual New Customer rows store customer-only profile fields on `database_customer_profiles` using the same customer/contact/address naming as `database_jobs`/`database_customer_addresses`. These profiles are merged into customer list/search/detail APIs using `profile:<id>` keys, have zero orders until a real order exists for the same customer, and are suppressed from list/search once a matching `database_jobs` customer exists to avoid duplicate rows.
- Customer contacts: `tblContact.ContactID` maps to `database_customer_contacts.source_contact_id`, `CustomerID` to `customer_id`, `AddressID` to `address_id`, `sTitle`/`sFirstname`/`sLastname` to split contact-name fields, `sTel`/`sFax`/`sMobile`/`sEmail` to the corresponding contact fields, `TraceStaffID` to `trace_staff_id`, and `dtCreate`/`dtEdit` to nullable source timestamps. `contact_address` is the formatted linked `tblAddress` row. The legacy `ynMailout` field is present in the MDB but is intentionally not shown in the current contact UI.
- Customer addresses: `tblAddress`, joined through `tblCustomer.invaddressid` / `tblCustomer.deladdressid`, selected `tblOrder.invaddressid` / `tblOrder.deladdressid`, and selected-customer `tblContact.addressid`. The importer writes address rows for customers that appear in the selected order snapshot. Imported jobs also store `invoice_address_id`, `delivery_address_id`, and formatted invoice/delivery address text from `tblAddress`.
- Line items: historical rows originate from `tblOrderItem` joined to `tblProduct`, `tblStyle`, `tblStyleColour`, `tblColour`, `tblStyleSize`, `tblSize`, `tblProductType`, and `tblSupplier`. Their positive `source_product_id` and imported snapshots remain immutable unless a user explicitly edits that order line, except that a fully matched placed Ralawise order replaces only `unit_cost` with the supplier order-detail discounted unit price. Canonically resolved/new lines additionally store `ralawise_catalog_variant_id`, exact child `ralawise_sku`, supplier style/colour/size codes, catalogue status, and sync timestamp; `legacy_source_product_id` preserves the original positive id when an operator explicitly changes a historical variant. `line_sort_order` is assigned during import from the legacy item order and can be updated manually from the Order Items drag handle.
- Products: normalized Ralawise styles/colours/variants are the active product source. Positive `database_products.source_product_id` rows remain keyed by `tblProduct.productid` as the historical compatibility layer populated from Access; unique Ralawise matches add exact catalogue identity/enrichment and match-audit fields without changing those ids. Catalogue-only compatibility rows use stable negative source/style IDs. The active product selector does not depend on Access rows, and an MDB product refresh must restore rather than erase the compact Ralawise links.
- Ralawise basket/order audit: `database_ralawise_basket_jobs` stores one durable attempt/result per DATABASE job, including `adding`/`basketed`/`ordered`/`failed` state, basket and placed-order snapshots, supplier order number/URL, quantities, warnings, errors, timestamps, basket sync state, and a revision incremented after each verified update. `database_ralawise_basket_lines` stores the exact SKU and quantity currently audited for each source order item plus the matched supplier order line, discounted unit/line price, and ordered timestamp. Audit rows are written before contacting Ralawise so timeouts and post-request crashes can be reconciled without duplicating a job; basket updates retain the previous audit until supplier read-back verification succeeds.
- Positions: `tblOrderPosition`: `orderpositionid` maps to `source_order_position_id`, `orderid` to `source_order_id`, source row order maps to `position_sort_order`, `sposition` to `position_name`, `memcolour` to `colour_notes`, and `sdesign` to `design_ref`.

## Supplier API Integrations

- PenCarrie calls use HTTPS `POST` form requests to the configured official `/gateway` endpoint. `pcgetstock` is available through the server-side client. PenCarrie authorizes the configured customer code only when the request originates from a fixed IPv4 address that PenCarrie has associated with that code; `PENCARRIE_STATIC_IP` is diagnostic metadata and cannot force the runtime to use that address.
- Ralawise inventory calls use `POST /v1/login` with top-level `user` and `password` JSON fields, cache the returned JWT until shortly before expiry, and send it as a bearer token to `GET /v1/inventory/:identifier`. The Ralawise user must separately be enabled for API access by Ralawise.
- Ralawise shop calls use a separate server-side session against `shop.ralawise.com`: load the anti-forgery token/cookies, sign in through `/Services/Authentication/SignIn`, snapshot `/services/cart/get`, add grouped exact variant SKUs through `/services/cart/AddMultiItemsToCart`, and apply or update the 15-character customer-name line reference and quantities through `/services/cart/updateBasket` where required. A DATABASE basket update first exact-compares the live referenced rows with its stored audit, modifies only those referenced rows, and exact-compares the final read-back with the desired saved Order Items. Adding or updating the basket does not place/checkout a supplier order. Placed-order confirmation uses `POST /services/orderhistoryservice/searchorders`, then loads the returned order-detail page and parses the exact supplier SKU, stored line reference, quantity, and discounted unit price.
- Supplier credentials, JWTs, and shop cookies remain server-side. The authenticated Hub API exposes only scoped Stock Ordering basket and placed-order sync actions; it never returns credentials/session material to the browser.

## Scripts

- `npm start`: starts `server.js`.
- `npm run import:database-mdb -- [PS_XP_tab.mdb] [--dry-run] [--append] [--insert-only]`: import full-history MDB jobs, contacts, addresses, positions, and products into DATABASE tables. Add `--years=2025,2026` for a scoped diagnostic import, `--products-only` to import only the full product catalogue, or `--insert-only` to add only source rows that do not already exist.
- `npm run verify:mdb-invoices -- [PS_XP_tab.mdb] [--max-mismatches=25]`: fail if source-backed `database_jobs.order_no` / `invoice_no` values differ from `tblOrder.lngOrderNo` / `lngInvoiceNo` in the supplied MDB, or if any DB invoice number is duplicated. `npm run verify:mdb-numbering` is an alias for the same critical numbering audit.
- `npm run import:ralawise-catalogue -- --file <path> --dry-run`: stream and audit a local Ralawise catalogue plus calculate exact database matches/cost changes without writes. Use `--apply --confirm-write` only after verifying the printed target.
- `npm run backfill:ralawise-line-items -- --dry-run`: audit historical line candidates/conflicts. `--apply --confirm-write` adds only exact canonical identity and verifies a before/after fingerprint of every other line field inside the transaction.
- `npm run verify:ralawise-catalogue`: run read-only normalized catalogue/product/status/import-run counts, line identity/integrity, image URL checks, approved Access links, and exact current Stock Ordering eligibility diagnostics.
- `npm run test:ralawise-catalogue`: runs focused parser, identity, reviewed/rejected matching, pricing, stable-ID, image, idempotency, weight, no-delete, dry-run write-safety, and historical line-write-scope tests.
- `npm run test:suppliers`: runs mocked PenCarrie/Ralawise protocol tests plus Ralawise website-basket, placed-order detail/discount-price parsing, and Stock Ordering plan/reconciliation tests.
- `npm run test:database-addresses`: runs focused customer-profile address route tests covering independent invoice/delivery persistence for existing profiles and first edits of imported-only customers.
- `npm run test:labels`: runs focused 4 × 6in label-layout tests covering QR removal, two-line customer/title wrapping, whole-word/no-hyphen rules, escaping, quantity bounds, numbered multi-page output, page breaks, and print startup.
- `npm run test:dtf`: runs DTF pricing, status, job-number, page-size, PDF-generation, packing, access-middleware, idempotent-schema, job creation/finalization, and signup-scope route tests.
- `npm run preflight:dtf-cloudinary`: uploads a temporary exact-size authenticated PDF through the same signed browser-upload contract, verifies Admin API page metadata and signed delivery, and destroys the temporary asset in a `finally` cleanup.
- `npm run preflight:dtf-cloudinary:large`: runs the same cleanup-safe check with a 249MiB one-page PDF and the production chunked-upload path.

## Known Risks And Maintenance Notes

- There is no general application test suite. DTF domain/access/layout/schema behavior, customer address profile persistence, supplier clients, and the Ralawise Stock Ordering basket/placed-order workflow have focused tests.
- The currently pinned `xlsx` dependency has published prototype-pollution and ReDoS advisories with no upstream patched release available through npm audit; MDB/CSV import inputs must remain operator-controlled.
- DTF premade PDF validation depends on Cloudinary returning PDF page count and dimensions for authenticated image resources, and PDF delivery must be enabled in the `brandduk` Cloudinary environment. EPS is intentionally rasterized to 300-DPI lossless PNG; PNG and PDF artwork are not flattened with the whole sheet.
- The 2026-07-21 `brandduk` production preflight accepted exact-size authenticated PDFs and 300-DPI EPS conversion, but its current account response reports a 20MiB maximum image/PDF asset size. The Hub supports signed 20MB chunk ranges and validates files through 250MB, but Cloudinary must raise the account-level image upload limit to at least 250MiB before sheets above 20MiB can complete; chunking does not bypass the account quota.
- DATABASE imports use an MDB snapshot for historical orders/products only. Run a fresh import whenever the source MDB copy changes, then verify that its canonical-link snapshot/restore completed; active product selection remains Ralawise-catalogue backed.
- Ralawise catalogue CSV exports are external snapshots rather than live inventory. Re-run the dry-run before every apply, preserve the reported ambiguity review, and use the JWT inventory API for current stock availability.
- The 2026-07-16 Stock Ordering audit found nine jobs with product lines: seven are fully exact-SKU eligible. Order 50333 remains blocked because its Portwest `DX416`, `DX413`, `PW379`, `DX457`, `PW275`, legacy `PW261`, and legacy `PW265` garments are absent from the supplied catalogue or collide with different current products. Order 51126 remains blocked on absent `70100` and `H830` variants. Do not guess substitute SKUs; select a current catalogue replacement on the order or obtain supplier-confirmed mappings.
- Cloudinary file bytes are external to Postgres; `test_dashboard_files` stores delivery metadata and best-effort asset cleanup can fail independently.
- The public `/test-scan` endpoint is intentionally unauthenticated but requires a valid HMAC signature generated with `SCAN_SECRET`.
- PenCarrie access depends on an external fixed-IPv4 whitelist tied to the customer code. Local or platform egress changes will cause authorization failure even when the gateway URL and customer code are correct.
- A normal Ralawise website user/password cannot use the JWT inventory API until Ralawise enables API access for that specific user. The basket and placed-order workflows use undocumented Ralawise website routes/HTML whose token, cookie, payload, endpoint, or order-detail markup may change; failures or partial matches must leave the DATABASE job unmarked so an operator can retry safely. Basket addition does not checkout or create a supplier order.
